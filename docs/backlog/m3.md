# M3 — Command layer, finishes, material library, scene server

Refined by the user-story agent (2026-10-26). Size: S ≤ ½ day, M 1–2 days, L 3–5 days. Layers: **Vitest**, **PW** (Playwright), **Manual**.

## Decisions
1. **Local-first.** Reducer, history, autosave and material library run in the browser; GitHub Pages stays fully functional. `apps/server` is an optional accelerator for multi-tab + MCP live sync.
2. **One pure reducer** `applyCommand(scene, envelope) → ApplyResult` in `packages/scene/src/commands/` — no clock/randomness, no mutation, structural sharing (untouched entities stay `===`).
3. **Inverses computed at apply time** (`inverse: Command`, JSON-serialisable); history/log entries store `{envelope, inverse}`.
4. **Atomic `batch`** (all-or-nothing, one undo step, depth 1) for LLM multi-step plans; `coalesceKey` merges rapid edits (colour drags).
5. **Undo is appended, never truncated** (`undoOf`); server mode = one shared linear stack.
6. **Concurrency:** last-writer-wins at command granularity; server log defines order; clients keep `confirmed + pending[]` and rebase by replay; failed pending commands dropped and reported as data.
7. **Materials:** static CC0 catalog in `apps/web/public/materials/` (processed WebP committed, no network in CI). Applying a library material first runs idempotent `material.define` so scenes stay self-contained. Library texture URLs use `lib:<slug>` (resolved to `${BASE_URL}materials/<slug>/`; unknown slugs never fetched). Paint ids are deterministic: `paint-<hex6>-<matt|satin|gloss>`.
8. **Scene stays `version: 1`** (additive changes only); envelope has its own `v`; `migrateScene`/`migrateCommand` scaffolding ships now.
9. **Deferred:** `moveWall` + room-polygon reconciliation (→ M6), camera pose in ViewState (→ M4), item commands (→ M5), KTX2, user-uploaded textures, per-author undo.

## Command catalogue (mirrored 1:1 by M4 MCP tools)
| type | payload |
|---|---|
| `material.define` | `{material}` — idempotent upsert |
| `wall.setFinish` | `{wallId, side: left\|right\|both, materialId\|null}` |
| `room.setWallFinish` | `{roomId, materialId\|null}` — expands via `roomWallSides` |
| `room.setFloor` / `room.setCeiling` | `{roomId, materialId\|null}` |
| `scene.setDefaults` | `{wall?, floor?, ceiling?}` |
| `site.set` | `{site: Partial<Site>}` |
| `light.add` / `light.update` / `light.remove` | `Light` / `{id, patch}` / `{id}` |
| `batch` | `{label, commands[]}` |

Envelope `{v:1, id (ULID), ts, author:{kind:user\|llm\|planner, name?, clientId?}, coalesceKey?, ifRev?, cmd}`. `ApplyResult = {ok:true, scene, inverse, changed, warnings} | {ok:false, errors:[{code, path, message, hint?}]}` with codes `invalid_command | unknown_entity | unknown_material | limit_exceeded | precondition_failed | not_supported | scene_invalid`. ViewState operations (sun time, presets, camera) are not commands.

## User decisions (M3 kickoff, 2026-10-26)
- Undo: **one shared history** in server mode.
- Texture library style: **warm French apartment** (oak/chevron parquet, cement tiles, smooth plaster, marble, linen wallpaper).
- Server connection on the public Pages site: **dev-only until M4** (`?server=` / local dev).
- Moving walls is **not a priority**. What matters is knowing **whether a wall is removable or structural** (load-bearing walls/façades can never be removed) → new story below. `moveWall` stays deferred (M6 at the earliest).

### M3.15 Structural vs removable walls — M
**As a** user/LLM **I want** each wall marked structural (load-bearing, façade, party wall) or removable (light partition) **so that** renovation ideas never propose removing a wall that can't go.
- Schema (additive): `Wall.structural?: boolean`. Default when absent: `true` for exterior/party walls and walls ≥ 0.15 m thick, `false` for thinner partitions — resolved by a pure `isStructural(scene, wall)` helper, documented. Charme 3205: façades, `w-landing`, `w-sdb-east` structural; 7 cm partitions removable (user can correct).
- Command `wall.setStructural {wallId, structural}` (undoable). Reserved rule for M5/M6: `wall.remove`/`opening.add` on a structural wall → `precondition_failed` with hint "structural wall".
- UI: badge + toggle in the wall properties panel; top-view overlay colouring structural walls (e.g. hatched dark) vs removable (light).
- AC: Vitest — defaults on both fixtures, command + undo, JSON-schema snapshot includes it; PW — toggling in the panel updates the badge and the overlay, undo restores.

### M3.16 Room-scoped wall finishes (user feedback 2026-10-26) — M
A wall side often spans several rooms (e.g. `w-north` inner face: alcôve, chambre 2, chambre 1; `w-west`: alcôve + séjour). Painting "this wall" must only paint the stretch inside the room where the user clicked.
- Schema: `Wall.roomFinishes` (per room, per side); `wall.setFinish` gains `roomId`.
- Precedence: per-wall-per-room > room "all walls" paint is overridden by later per-wall paint and vice versa (room repaint clears that room's per-wall finishes).
- UI: "This wall (Séjour side)" scope uses the room at the click point; "Both sides" paints each side within its adjoining room.
- AC: painting w-west in séjour leaves the alcôve stretch unchanged; painting w-north in chambre 1 leaves alcôve/chambre 2 unchanged; undo exact.

### M3.17 Walk-mode comfort (user feedback 2026-10-26) — S
- Door leaves render translucent (~0.35 opacity) in walk mode only.
- "Lights on in walk mode" preference (default on): walk mode shows all lamps on + 0.5 EV via a derived effective-lighting layer; leaving walk restores the user's lighting exactly.
- Charme 3205 door swings per user: bedrooms/alcôve open into the room, bathroom + WC into the hall, séjour door into the séjour, front door opens outwards onto the landing.
- **Status:** shipped. "This wall (<room> side)" uses the room at the click point (`Selection.roomId`/`along`, from the hit point and `wallSideRooms(...).segments`); "Both faces here" batches one room-scoped `wall.setFinish` per face; reset clears only that room's stretch; `__flat.select({wallId, side, roomId})` selects a face as if clicked in that room. E2E: `e2e/room-finishes.e2e.ts`.

### M3.17 Walk-mode comfort (lead request, 2026-10-26) — S
- Door leaves are drawn at 0.35 opacity in walk mode (a second material instance, `builtin:door-walk`; opaque in orbit/top; shadows unaffected).
- "Lights on in walk mode" (default on, remembered): walk mode lights every lamp and adds +0.5 EV as a derived `effectiveLighting` layer; the stored lighting is untouched, so leaving walk mode restores it exactly. E2E: `e2e/walk-comfort.e2e.ts`.
- The front door of Charme 3205 swings out onto the landing (`door-entry.swing = "left"`).

### M3.18 Camera POV and controls (user request, 2026-10-28) — S
- Person ghost in orbit and top views: translucent figure at the person height standing at the walk start (the last walk pose, else the default start); draggable (slides along walls, stays inside the flat), "Walk" starts from it; "Show person" preference (default on). Drawn with the HD library figure `sketchfab:person_standing` (CC-BY-4.0, "3d people standing smooth" by dchant design; 1830 triangles, 11 KB) scaled uniformly to the height, or the parametric 8-heads mannequin when the file cannot be loaded. E2E: `e2e/pov.e2e.ts`.
- Stick-like keys by physical position (`KeyboardEvent.code`; ZQSD on AZERTY): arrows are the left stick (move / strafe in walk, pan the target in orbit and top), W/A/S/D the right stick (look in walk; orbit around the target in orbit), about 90 deg/s with acceleration, pitch clamped to +-80 degrees. A selected item keeps the arrows (nudge). Gamepad (left/right stick, 0.15 deadzone) supported. Help overlay shows ZQSD when `navigator.keyboard.getLayoutMap()` reports AZERTY, both labels otherwise.
- Walk fov 60 degrees vertical (was 50), near plane 0.03 m.
